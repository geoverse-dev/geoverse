Portolan SDKs explore a consistent way to read, construct, and evolve directory-based geospatial catalogs — with shared conformance tests across implementations.

WHAT THE SDKs COVER

From discovering a catalog to preparing its output.

The goal is a reusable catalog abstraction, not a library tied to a particular storage service. The read and write paths are complementary, and implementations can evolve at different speeds.

01

Read & navigate

Open existing directory-based catalogs, inspect their structure, follow references, and discover their datasets and metadata through a consistent API.

Catalog discoveryMetadata
02

Build & update

Construct and modify an in-memory catalog representation before deciding how or where to persist the resulting artifacts.

Catalog modelWrite workflows
03

Plan materialization

Keep the catalog model separate from the responsibility of writing files to local storage, object stores, or other destinations.

Storage-agnostic designRound-trip validation
Development direction: Writing and round-trip support are part of the evolving SDK design. The capabilities above describe the intended scope, not a guarantee that every feature is available in every language implementation today. Consult each repository for its current status.
DESIGN PRINCIPLES

Built for interoperable geospatial tooling.

One mental model

Use a consistent vocabulary for catalogs and their contents across languages.

Portable by design

Work with catalog structures without coupling the core API to a particular filesystem or cloud provider.

Testable behavior

Use shared fixtures and expectations to catch differences between implementations.

SHARED VALIDATION

How Portolan Conformance fits in.

A common specification is most useful when independent SDKs can demonstrate that they interpret it consistently. The portolan-conformance project provides a shared validation layer.

What this helps verify

  • Catalog interpretation and structural consistency.
  • Expected behavior against shared fixtures.
  • Cross-language alignment as APIs evolve.
  • Read/write round trips as writing support is developed.

Conformance tests validate implementations against the shared contracts; they do not replace the specifications themselves or imply that every SDK has completed every test.
